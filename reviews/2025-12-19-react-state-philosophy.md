# On「React の状態管理の歴史と、最新 API に込められた React の思想」

> Original: https://zenn.dev/zozotech/articles/ebf38b7ab4aff0
> Reviewed: 2025-12-19
> Model: Claude Opus 4.5

---

## 記事の主張

この記事は、React の状態管理の歴史を「UI = f(state)」という思想で一貫して説明する。

> 「React は UI のための言語であり、状態の所有者ではない」
> 「状態は React の外側に置かれ、React はその状態を常に同期し続ける存在になる」

Redux → Recoil → Zustand → `useSyncExternalStore` という流れを追い、すべてが「状態は外部に、React は同期役」という思想に収束したと結論づける。技術選定に悩むエンジニアにとって、歴史を思想レベルで整理した価値ある記事だ。

しかし、この「一貫した思想」という物語には、見過ごせない問題がある。

---

## 問題1: 歴史の書き換え

記事は Redux を「フロントエンド開発に革命をもたらした」と評価し、React の思想の体現として位置づける。

**事実は違う。**

Redux が登場した2015年、コミュニティの反応は賛否両論だった。ボイラープレートの多さ、Action/Reducer の冗長さへの批判は激しく、Redux の作者 Dan Abramov 自身が翌年「[You Might Not Need Redux](https://medium.com/@dan_abramov/you-might-not-need-redux-be46360cf367)」で「Redux を使いすぎるな」と警告した。

**Redux は「思想の体現」として歓迎されたのではない。批判されながら、それでも生き残ったのだ。**

Recoil はどうか。記事は「宣言的な依存グラフ」による進化と位置づけるが、Meta が開発したにもかかわらず実験的プロジェクトのまま普及しなかった。本当に「React の思想に沿った次のステップ」なら、なぜ失敗したのか。記事はこの問いに答えていない。

Zustand の人気は「思想への共鳴」ではない。「Redux が面倒だから」という消去法だ。npm trends を見れば、Zustand が伸びた時期と Redux への不満が噴出した時期は一致する。

つまり、**成功したものを後から見て「思想に沿っていた」と説明しているだけ**だ。これは歴史の分析ではなく、歴史の書き換えだ。

---

## 問題2: 論理の矛盾

記事は「状態は React の外側に置かれる」を React の核心的思想とする。

しかし React 自身の動きを見よ。

- **Context API**: React 内部でグローバル状態を管理する仕組み
- **Suspense for Data Fetching**: React が非同期状態を直接扱う拡張
- **Server Components**: 状態をサーバーに移動させる発想
- **use() Hook**: Promise を React が直接消費する API

これらはすべて「状態を React の内側に引き込む」方向だ。**「状態は外部に」という原則と明らかに矛盾する。**

記事が描く「一貫した思想」は、React 自身が否定しつつある。

---

## 問題3: 結論の放棄

記事は最後に「正解はない」と結ぶ。

ここまで「React の思想」を軸に壮大な物語を語っておいて、結論が「正解はない」では読者は困惑する。

- 思想の一貫性を主張するなら、「この思想に沿ったものが正解に近い」と言い切るべきだ
- 「正解はない」と言うなら、なぜ Redux → Recoil → Zustand を「思想の実現」として語ったのか

**これは論理的に両立しない。** 記事は自らの結論で自らの前提を崩している。

---

## 本当の教訓

この記事から学ぶべきは「React の思想に沿え」ではない。

**「思想は後付けである」** ということだ。

Redux が正解かどうかは2015年にはわからなかった。今選ぶライブラリが5年後に「思想に沿っていた」と言われるかもわからない。成功したものを振り返って「思想があったから成功した」と説明するのは簡単だが、それは予測には使えない。

技術選定において信頼できるのは、思想ではなく実利だ。学習コスト、チームのスキルセット、プロジェクトの規模。Zustand が選ばれたのは思想ではなく「楽だから」だ。その正直さの方が、後付けの思想より信頼できる。

---

### Strength

* Redux → Recoil → Zustand → useSyncExternalStore の流れを整理した構成力
* 「なぜこうなったのか」を問う姿勢
* 「先人たちの思考の過程を学ぶ」という動機は誠実

### Weakness

* 歴史をリアルタイムで見た人の体験と乖離した「思想の一貫性」物語
* Context API、Suspense、Server Components との矛盾を無視
* 「正解はない」という結論が、記事全体の論旨を自己否定

---

### One thought

「思想があったから成功した」のか、「成功したから思想があったと言われる」のか。

この記事を読んで「React の思想に沿ったものを選ぼう」と思った人は、一度立ち止まってほしい。その「思想」は、5年後にまだ有効だろうか。それとも、次の成功者が現れたとき、また別の「思想」が発見されるのだろうか。
